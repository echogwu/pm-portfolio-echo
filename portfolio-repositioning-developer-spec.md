# Portfolio Repositioning — Developer Execution Spec

## Goal

Reposition Echo's portfolio for data infrastructure / real-time platform product roles, with Hightouch as the immediate target.

The site should optimize for a hiring manager skimming quickly and deciding:

1. Echo has already done this kind of work.
2. Echo can operate at the required product level.
3. Echo has strong product judgment in technically complex systems.
4. There is enough depth to justify clicking into the case studies.

The site should prioritize **role fit first, supporting depth second**.

# 7. Visual Hierarchy

The page should visually communicate:

- Klaviyo = strongest role-fit proof
- Gainbridge = strong supporting proof
- Lyft + founder experience = range and depth
- Engineering + MBA = foundation

Use:

- large typography for Klaviyo
- more whitespace around Klaviyo
- one restrained accent treatment for the featured card
- smaller typography and quieter visual treatment as the page moves downward
- generous whitespace overall

Avoid:

- six equal-size boxes
- equal font sizes across all experiences
- heavy gradients
- excessive visual decoration
- treating every career stop as equally important

Proportion is part of the message.

# 8. Case Study Positioning

Each case study should emphasize product judgment rather than process.

Recommended order:

1. Problem / business context
2. What I owned
3. Key product decisions
4. Trade-offs
5. Outcome / business impact
6. Risks / learnings
7. Supporting artifacts

Avoid leading with:

- "First I interviewed..."
- "Then I created..."
- "My process was..."

Prefer language such as:

- I owned...
- I reframed...
- I decided...
- I defined...
- I set...
- I chose...
- I established...
- I narrowed...
- I changed...
- I aligned...

The reader should understand **what decisions Echo made and why those decisions mattered**.

# 9. Klaviyo Flagship Case Study

This should be the strongest and most relevant case study on the site.

Do not frame the work narrowly as "data retention."

Use:

> Evolving the Event Data Platform

The case study should make clear that the work concerns the broader event-data architecture, including:

- ingestion
- event storage
- event serving
- APIs
- downstream product requirements
- latency / freshness expectations
- SLOs
- cost
- customer experience
- rollout risk
- hot vs. cold access patterns
- architectural trade-offs

The core framing should be:

> As event volume and infrastructure cost scaled, the question became what the event platform should guarantee to each downstream product—and where the system could flex.

The case study should demonstrate ownership of the **product contract for the platform**, not just execution of a storage policy.

# 10. Product Artifacts Page

Keep the artifacts page.

The current relationship between case studies and artifacts is valuable.

Do not treat the page as a random folder.

Treat it as an **evidence index**.

Group artifacts by the case study they support.

For each artifact, show:

1. Artifact name
2. Artifact type
3. One-line context
4. Decision supported
5. What the viewer should notice
6. Link back to the relevant case study

Suggested artifact types:

- Decision framework
- Architecture model
- Data model
- Object relationship map
- Rollout plan
- Product requirements
- Trade-off analysis
- Measurement framework

Artifacts should feel like receipts for the product thinking shown in the case studies.
